## P0 — известные ограничения, которые видны команде

Эти пункты команда **обязательно заметит** в первый месяц использования. Их стоит закрыть раньше нового функционала.

### P0.1 PII scrubber pass перед эмбеддингом

**Откуда:** [GDPR-RELEASE.md → пункт 6 «Минимизация»](GDPR-RELEASE.md), известный риск.
**Что:** перед отправкой текста в OpenAI прогонять regex/NER pass, который заменяет email-адреса, телефоны, номера паспортов на токены `<EMAIL>` / `<PHONE>`. Эмбеддинг остаётся семантически осмысленным; PII не покидает наш контур.
**Почему P0:** команда уведомлена «не клади PII в задачи», но в реальности люди забывают. Технический митигатор закрывает GDPR-риск без полагания на дисциплину.
**Размер:** 2-3 дня (regex для email/phone в первой итерации; NER-based в будущем).
**Кто:** Костя/Вова.

### P0.2 TTL job для AIUsageLog / AIAgentActionLog

**Откуда:** [docs/processing-register.md → пункт 5 «Сроки хранения»](docs/processing-register.md) — заявлено 2 года, сейчас храним вечно.
**Что:** Celery beat job, который раз в сутки удаляет `AIUsageLog` и `AIAgentActionLog` старше 2 лет. Изоляция: с фильтром по workspace на случай разных retention-политик в будущем.
**Почему P0:** заявленный retention обязывает по GDPR. Без cron'а каждый день мы нарушаем reg.
**Размер:** 1 день.
**Кто:** Костя/Вова.

### P0.3 Полный TZ 3.2 (саммари / генерация)

**Откуда:** TZ 3.2 — заявлен в архитектуре, но в этой версии не реализован (BUDGET.md, аудит feature тегов). `FEATURE_SUMMARIZE` определён, но без caller'a.
**Что:** Кнопка `Summarize` в задаче с длинной дискуссией. Промпт + claude_sse с `feature=FEATURE_SUMMARIZE`. UI компонент.
**Почему P0:** команда ожидает увидеть в `User Guide`; если фичи нет — рассинхронизация ожиданий.
**Размер:** 3-4 дня (backend + UI).
**Кто:** Костя/Вова + Эдик.

### P0.4 Полный TZ 4.x (bulk-операции через NL)

**Откуда:** TZ 4.x — заявлен, не реализован. `FEATURE_BULK` определён, без caller'a.
**Что:** Эндпоинт `POST /api/ai/bulk/`, который принимает NL-команду, парсит через Claude в **план изменений**, возвращает план (без выполнения), пользователь подтверждает в UI, тогда `acl.filter_ids_by_acl` + apply.
**Почему P0:** одна из 4-х основных фич, заявленных команде.
**Размер:** 5-7 дней (с правильным confirmation-flow).
**Кто:** Костя/Вова + Эдик.

## P1 — UX-улучшения, которые поднимут adoption

### P1.1 Кеш ответов поиска

**Откуда:** мониторим в первые дни — если повторяющиеся запросы (например, «что у меня открыто?» утром) разогревают модель N раз.
**Что:** в Redis с TTL=30 минут кешировать `(workspace_id, user_id, query_hash) → response`. Поскольку retrieval тоже детерминирован при том же индексе, кеш сейв ~70% повторных запросов.
**Почему P1:** ускоряет UX (моментальный ответ), снижает расход.
**Размер:** 2 дня.

### P1.2 Feedback-кнопка прямо под ответом поиска

**Откуда:** TZ 6.8 «сбор фидбэка» сейчас идёт через Slack; быстрее, если 👍/👎 прямо в UI.
**Что:** под ответом поиска две кнопки. По клику пишется в новую таблицу `AISearchFeedback(workspace_id, user_id, query, response_id, rating, comment?)`. Для admin — отчёт через эндпоинт.
**Почему P1:** в 10× больше сигнала на качество поиска, чем устный фидбэк в Slack.
**Размер:** 2 дня.

### P1.3 Объяснение «почему этот источник»

**Откуда:** наблюдение в фазе 1 — пользователи иногда не понимают, почему ИИ нашёл именно эти задачи.
**Что:** под каждым `source` ссылка показывать топ-3 совпавших чанка с подсветкой. (mini-rerank UI).
**Почему P1:** trust-фактор.
**Размер:** 3 дня (backend + UI).

### P1.4 «Стоп-кран» для агента на одной задаче

**Откуда:** TZ 5.6 даёт workspace-level и agent-level toggle, но не per-issue.
**Что:** в задаче кнопка «отключить агента для этой задачи». Записать в `AIAgentExclusion(issue_id)`. Триггер агента читает этот список.
**Почему P1:** иногда задача активно меняется командой, и комментарии агента шумят.
**Размер:** 1-2 дня.

### P1.5 Расширенный дашборд расхода

**Откуда:** TZ 6.3 сделан минимально; PM просит больше срезов после первого месяца.
**Что:** кастомный диапазон дат (не только preset-ы), drill-down по проектам, экспорт в CSV, сравнение month-over-month.
**Почему P1:** PM-инструмент, помогает отчитываться перед руководством.
**Размер:** 2 дня.

## P2 — функциональные улучшения, расширяющие use-cases

### P2.1 Поиск по нескольким воркспейсам сразу

**Откуда:** запросы типа «у меня есть задача про X в любом из моих воркспейсов?».
**Что:** новый эндпоинт принимает `workspace_ids[]`, выполняет retrieval параллельно (с проверкой членства caller-а в каждом), мерджит топ-K.
**Размер:** 3 дня.
**Риск:** ACL-граница между воркспейсами (CLAUDE.md inv. 1). Тестировать тщательно.

### P2.2 Внутренний reranker

**Откуда:** наблюдение качества — иногда первые 1-3 результата ИИ-поиска не самые релевантные.
**Что:** после top-K embedding retrieval — rerank через cross-encoder (Cohere Rerank API или local sentence-transformers).
**Размер:** 3-4 дня.
**Trade-off:** дополнительная стоимость + latency.

### P2.3 Embedding миграция на large модель

**Откуда:** если P2.2 не даёт нужного качества — попробовать `text-embedding-3-large` (3072 dim). 6× дороже, может лучше.
**Что:** добавить `large` в `ai/pricing.py`, миграцию HNSW индекса под новую размерность, повторный backfill.
**Размер:** 1 день кода + ~$N на повторный backfill.
**Решение:** делать только если P2.2 неоднозначна.

### P2.4 Воркспейс-сценарии агента (custom playbooks)

**Откуда:** разные команды хотят разное поведение агента.
**Что:** конфигурация per-workspace: «триаж: ✓», «дедуп: ✓», «черновики: ✗», + custom scenario через скрипт-плагин. Сейчас сценарии хардкодены в `agent_worker.run_agent_body`.
**Размер:** 5-7 дней.
**Trade-off:** security review: custom playbook не должен обходить white-list инструментов.

### P2.5 Streaming для саммари/триажа

**Откуда:** сейчас стримим только search; саммари ждёт «весь ответ за раз» — медленно для длинных дискуссий.
**Что:** перевести summarize / triage через `claude_sse` (уже async-готов для search).
**Размер:** 1-2 дня.

## P3 — стратегические шаги

### P3.1 Self-hosted reranker / embedding

**Откуда:** GDPR / cost optimisation в долгую.
**Что:** на собственном сервере крутить `bge-small-en` (embedding) или mini-LM (rerank). Уход от OpenAI для эмбеддингов = ~$0 биллинга, без internat. трансфера.
**Размер:** 2-3 недели.
**Trade-off:** требует GPU или нагружает CPU. Качество может быть хуже text-embedding-3-small.

### P3.2 Multi-tenant SaaS

**Откуда:** если planeAI вырастет в продукт для других команд.
**Что:** нет сейчас в архитектуре; потребует контрактного DPA с клиентом, billing-слоя, изоляции вплоть до per-tenant pgvector index.
**Размер:** месяцы.
**Решение:** только если PM-команда определит как продукт-стратегию.

### P3.3 Multilingual поддержка

**Откуда:** на staging пробовали английский и русский — английский ощутимо лучше отвечает (большая выборка обучения).
**Что:** уделить внимание prompt'ам на русском, переключить `claude-sonnet-4-6` → `claude-opus-*` для не-английских контекстов (опционально).
**Размер:** 3-5 дней + тесты с двумя языками.

### P3.4 Audit-trail для пользователя

**Откуда:** GDPR Art. 15 — «что обо мне обрабатывалось».
**Что:** эндпоинт «выдай мне все мои AIUsageLog за период», пользователь видит свои использования + что именно отправлялось (где applicable). Сейчас это видит только admin.
**Размер:** 2 дня.

## Контракт на phase 2

- **Длительность:** 1 спринт (2 недели) на каждые ~3 P0 + 2-3 P1.
- **Приоритеты пересматриваются каждый понедельник** — PM на основе свежих метрик и фидбэка решает, что идёт в текущий спринт.
- **P0 закрываются раньше P1/P2/P3** — не «давайте сделаем что-нибудь интересное», а «закрыли заявленный TZ-функционал, потом расширяем».
