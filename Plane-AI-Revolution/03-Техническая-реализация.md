# Техническая реализация: чтобы всё реально работало

> Как multi-agent система функционирует в Plane на практике — координация, событийный поток, принятие решений, и что критично для прода.

---

## Общая схема исполнения

```
Plane (изменение) → [post_save signal] → [Event Stream] → [Celery]
                                                              ↓
                                                      [ORCHESTRATOR]
                                                   решает, нужен ли агент
                                          ┌──────────────┼──────────────┐
                                      [MONITOR]      [EXECUTOR]      [ANALYST]
                                          └──────────────┼──────────────┘
                                                  [Decision Layer]
                                              сам / спросить человека
                                          сам ↓              ↓ эскалация
                                   действие в Plane      алерт человеку
                                   (API + ACL)
```

---

## 1. Event Stream — как система узнаёт об изменениях

Агенты не опрашивают Plane постоянно — реагируют на события. Расширяем сигналы из ТЗ 1.4:

```python
@receiver(post_save, sender=Issue)
def on_issue_change(sender, instance, created, **kwargs):
    if not _ai_enabled(instance.workspace_id):
        return
    if getattr(instance, '_modified_by_agent', False):  # защита от петли
        return
    event = {
        "type": "issue_created" if created else "issue_updated",
        "issue_id": str(instance.id),
        "project_id": str(instance.project_id),
        "changed_fields": _get_changed_fields(instance),
    }
    transaction.on_commit(lambda: process_event.delay(event))
```

**Важные события:** issue_created → ORCHESTRATOR; issue_updated → MONITOR; issue_blocked → EXECUTOR; goal_created → полный цикл планирования.

---

## 2. ORCHESTRATOR — координация без хаоса

Сложность multi-agent: агенты не должны конфликтовать (двое меняют одну задачу) или зацикливаться (A триггерит B, B триггерит A).

Реализация на **LangGraph** — граф состояний, ORCHESTRATOR маршрутизирует событие нужному агенту, после действия — назад к анализу или конец.

### Защита от конфликтов
- **Redis-лок** `agent_lock:{issue_id}` — пока один агент работает с задачей, другой ждёт
- **Лимит глубины** графа — не больше N переходов за запуск (защита от циклов)
- **Идемпотентность** — каждое событие обрабатывается раз (дедуп по event_id)

---

## 3. Decision Layer — когда агент сам, когда спрашивает

Сердце безопасности. Матрица «тип действия → уровень риска»:

```python
DECISION_MATRIX = {
    "set_label":        AUTO,      # обратимо, безопасно
    "set_priority":     AUTO,
    "suggest_assignee": NOTIFY,    # предложение, не назначение
    "add_comment":      AUTO,
    "reassign_task":    CONFIRM,   # меняет чужую работу
    "change_deadline":  CONFIRM,
    "create_60_tasks":  CONFIRM,   # массовое — показать превью
    "simplify_scope":   ESCALATE,  # стратегическое
    "hire_freelancer":  ESCALATE,  # затраты
    "delete_anything":  None,      # ЗАПРЕЩЕНО всегда
}
```

**Принцип:** обратимое и мелкое — сам; необратимое, дорогое, стратегическое — человек; удаление — никогда. Если действие на критическом пути — уровень повышается.

## 4. PLANNER — как декомпозиция создаёт задачи

Пайплайн: RAG (похожие проекты) → Claude декомпозирует в JSON → **ВАЛИДАЦИЯ** → создание в Plane через API.

### Защита от галлюцинаций PLANNER
- Валидация графа зависимостей — нет циклов (топосортировка)
- Проверка дедлайна — сумма по критпути ≤ доступное время
- Лимит задач — 60, не 600 (защита от runaway)
- Дубли — проверка похожести через эмбеддинги
- **Превью человеку** — PLANNER создаёт черновик → CONFIRM → человек видит план до создания

При создании задач — флаг `_modified_by_agent=True` (защита от петли событий).

## 5. MONITOR + Prediction — предсказание задержек

Учится на `TeamVelocity` (оценка vs факт), которая копится с базовой версии.

```python
def check_risks(project_id):
    for issue in active_issues(project_id):
        features = extract_features(issue)  # оценка, прошло, прогресс, исполнитель, точность оценок
        risk_proba = prediction_model.predict_proba(features)
        if risk_proba > 0.7:
            risk = create_risk(issue, confidence=risk_proba, impact=compute_impact(issue))
            if risk.impact == "critical":
                escalator_handle(risk)
```

### Модель (реалистично)
- **Не нейросеть, а LightGBM** на табличных признаках — быстро, объяснимо, мало данных нужно
- **Холодный старт:** пока истории мало — эвристики (прогресс < линейного → риск)
- **Переобучение** раз в неделю
- **Честность:** confidence показывается, не выдаём догадку за факт

## 6. EXECUTOR — назначение с учётом реальности

Скоринг кандидатов: текущая загрузка + навыки (из истории) + доступность. Лучший кандидат → AUTO для мелочи или NOTIFY (предложение) для значимого.

## 7. Что критично для прода (реализм)

### Бюджет токенов — иначе разорение
Multi-agent жрёт МНОГО токенов (каждое событие → цепочка агентов).
- Жёсткий лимит на цикл обработки (расширяем guard 1.7)
- Дешёвая модель (Haiku) для рутины — MONITOR/триаж
- Дебаунс: пачка изменений за 10с → один запуск
- Prompt caching системных промптов

**Реальная оценка:** активный проект на 5 человек = сотни событий/день. Без оптимизации — десятки $/день. С оптимизацией — единицы. Мониторить с первого дня (дашборд 6.3).

### Нагрузка на сервер
**8 ГБ впритык** уже для базовой версии. Multi-agent добавляет LangGraph-оркестрацию, event stream, ML-модель в памяти. **Для революционной версии 16 ГБ (NLs-4) — не комфорт, а необходимость.** Честно: эта версия тяжелее.

### Защита от runaway
- **Circuit breaker:** агент сделал > N действий за час → автостоп + алерт
- **Kill switch:** одна кнопка «выключить всех агентов» (флаг, как ROLLBACK.md)
- **Полный аудит:** каждое действие в AgentAction с обоснованием
- **Лимит автономных действий** между эскалациями

### Холодный старт
Первые недели нет данных: PLANNER оценивает по RAG или консервативно, MONITOR на эвристиках, честно показываем низкую уверенность.

## 8. Порядок внедрения (чтобы не сломать)

Нельзя включить 7 агентов сразу. Поэтапно, каждый за флагом:

1. **PLANNER** — режим CONFIRM (предлагает план) — безопасно, видна польза
2. **MONITOR** — только наблюдение + алерты — копит данные
3. **EXECUTOR** — с NOTIFY (предлагает), потом AUTO для мелочи
4. **ESCALATOR** — когда MONITOR накопил точность
5. **ANALYST** — когда есть история
6. **COMMUNICATOR** — отчёты, низкий риск
7. **ORCHESTRATOR** — координация, последним, когда каждый проверен

На каждом шаге — приёмка на staging, gate перед следующим агентом.

## Связь с базовой версией

Надстройка над базовыми 7 спринтами, не замена:
- RAG из спринта 2 (контекст агентов)
- Agent loop из спринта 4 (function-calling)
- Простые агенты спринта 5 (триаж/дедуп) как фундамент
- Учёт токенов/бюджет спринта 1
- ACL везде (границы прав)
- Kill-switch спринта 6 (откат)
