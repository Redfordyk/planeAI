## 🎯 Цель

Механизм безопасного выполнения write-операций: модель предлагает массовое изменение → мы фильтруем задачи по правам записи → возвращаем пользователю превью с подписанным токеном → выполняем ТОЛЬКО после явного подтверждения.

## 📋 Контекст для Claude Code

Самое опасное место спринта. Инструкция могла прийти из недоверенного источника (или модель неверно поняла). Поэтому: (1) ACL-фильтр по праву ЗАПИСИ (filter_ids_by_acl из 0.6), (2) превью с числом задач, (3) подписанный токен, чтобы выполнить можно было только то, что подтверждено, (4) повторная ACL-проверка при выполнении.

## ✅ Что сделать

```python
# ai/agent.py (дополнение)
from django.core.signing import Signer, BadSignature
import json
from ai.acl import filter_ids_by_acl

signer = Signer()

def _prepare_confirmation(tool_use, user):
    requested = tool_use.input["work_item_ids"]
    confirmed_ids = filter_ids_by_acl(requested, user)        # право ЗАПИСИ!
    payload = {**tool_use.input, "work_item_ids": confirmed_ids}
    return {
        "type": "confirm",
        "action": "bulk_update_work_items",
        "confirmed_ids": confirmed_ids,                       # ← фронт показывает это
        "rejected_count": len(requested) - len(confirmed_ids),
        "params": {k: v for k, v in tool_use.input.items() if k != "work_item_ids"},
        "token": signer.sign(json.dumps(payload)),            # подписанное действие
    }

# отдельный эндпоинт ВЫПОЛНЕНИЯ после подтверждения
def execute_confirmed(user, token):
    try:
        payload = json.loads(signer.unsign(token))
    except BadSignature:
        raise PermissionError("Недействительный токен действия")
    # ПОВТОРНАЯ ACL-проверка (права могли измениться)
    ids = filter_ids_by_acl(payload["work_item_ids"], user)
    updated = _apply_bulk_update(ids, payload)                # ORM-обновление
    return {"updated": len(ids)}
```

Требования:
- `filter_ids_by_acl` проверяет право ЗАПИСИ, не только членство (ACL.md, 0.6).
- Токен подписан — нельзя подменить список ID на стороне клиента.
- При выполнении — ПОВТОРНАЯ ACL-проверка (defense-in-depth).
- Аудит: записать в лог, кто/что/когда выполнил (заготовка для аудита агентов 5.x).

## ✅ Definition of Done

- [ ] Write-операция возвращает превью с `confirmed_ids` и `rejected_count`
- [ ] Задачи без права записи отфильтрованы (viewer не может, member/admin может)
- [ ] Действие подписано, подмена ID на клиенте невозможна
- [ ] Выполнение — отдельным эндпоинтом, после подтверждения
- [ ] Повторная ACL-проверка при выполнении
- [ ] Действие пишется в аудит-лог
- [ ] Тесты (4.5): ACL-фильтр, подпись, повторная проверка

## ⚠️ Важно (грабли из отладки)

1. Контракт: возвращаем `confirmed_ids` (не просто `pending`) — фронт (4.4) и тест (4.5) ждут именно это поле. Согласовано.
2. ACL проверяется ДВАЖДЫ: при подготовке и при выполнении. Между ними права могли измениться.
3. Никогда не выполнять write по списку ID из запроса напрямую — только из подписанного токена + ACL.
