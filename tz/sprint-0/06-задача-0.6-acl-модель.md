## 🎯 Цель

Точно описать модель прав доступа Plane: как определить, к каким проектам у пользователя есть доступ и **с какой ролью** (viewer / member / admin). Это фундамент для двух критичных вещей: фильтрации поиска по правам и проверки прав на запись в bulk-операциях.

## 📋 Контекст для Claude Code

В нашем коде есть две функции, которые ОБЯЗАНЫ опираться на реальную модель прав:
- `allowed_projects(user, workspace_id)` — список проектов, видимых пользователю (для retrieval-фильтра).
- `filter_ids_by_acl(work_item_ids, user)` — оставить только задачи, к которым у пользователя есть доступ **на запись** (для bulk-update).

Раньше мы упрощали до «членство = доступ», но bulk-update требует именно права записи, а не только просмотра. Нужно разобраться с ролями.

## ✅ Что сделать

1. На основе `SCHEMA.md` (задача 0.2) найти модель членства (предположительно `ProjectMember`) и её поле роли.
2. Определить значения ролей и какие из них дают: чтение / запись / админ.
3. Проверить, есть ли уровень воркспейса (WorkspaceMember) поверх проектного.
4. Реализовать и протестировать в shell две функции:
   ```python
   # ai/acl.py
   def allowed_projects(user, workspace_id) -> list[uuid]:
       """Проекты воркспейса, где user — участник (любая роль = чтение)."""

   def filter_ids_by_acl(work_item_ids, user) -> list[str]:
       """Только задачи, к проектам которых у user есть право ЗАПИСИ."""
   ```
5. Задокументировать матрицу ролей в `ACL.md`.

## ⚠️ Важно

`filter_ids_by_acl` — предохранитель от того, чтобы ИИ изменил чужие задачи «потому что модель так решила». Право записи проверяется в КОДЕ, всегда. Не упрощай до членства, если у Plane есть viewer-роль без записи.
